Native API · 1С:Предприятие 8.3

1С и RabbitMQ — напрямую

Внешняя компонента, которая учит 1С работать с очередями: отправлять сообщения, получать их и не терять по дороге. Подключается как обычный макет конфигурации, без шины и промежуточных сервисов. Работает на Windows и Linux, в 32 и 64 битах.

Что это даёт разработчику 1С

Компонента говорит с брокером по AMQP напрямую из встроенного языка. Ни промежуточного сервиса, ни HTTP-обёртки, ни 1С:Шины — очередь становится обычным объектом, с которым работают из кода.

Ставится как общий макет

ZIP с бинарниками добавляется в конфигурацию как макет «Двоичные данные» и уезжает вместе с ней. Ничего не нужно устанавливать на машины пользователей и держать рядом отдельную службу.

Сообщения приходят сами

После BasicConsume компонента вызывает ОбработкаВнешнегоСобытия и передаёт тело, deliveryTag и свойства. Регламентное задание, которое дёргает очередь раз в минуту, не нужно — и задержки в эту минуту тоже.

Есть и режим опроса

В фоновом задании на сервере, где внешних событий нет, работает BasicConsumeMessage: забрать очередное сообщение по требованию. Одна и та же компонента и на клиенте, и на сервере.

Подтверждаете вы, а не компонента

BasicAck вызывается после того, как документ проведён. Не получилось — BasicReject вернёт сообщение в очередь или отбросит. Пока подтверждения нет, сообщение у брокера живо.

Темп приёма под контролем

Prefetch задаёт, сколько сообщений отдавать сеансу разом, — база не захлебнётся на пике и не будет простаивать, когда работы много.

Топология из встроенного языка

DeclareExchange, DeclareQueue, BindQueue и аргументы очереди — TTL, dead-letter, приоритеты. Схему создаёт сама конфигурация при запуске, без похода к администратору брокера.

Свойства сообщения целиком

CorrelationId, MessageId, ReplyTo, ContentType, Type, Expiration, приоритет и произвольные заголовки — то, на чём строится сопоставление ответа с запросом и маршрутизация.

Пощупать можно до внедрения

Исходный код открыт — его можно прочитать и собрать самому, это важно для компоненты, которая работает внутри процесса платформы. Демо-стенд с готовыми обработками для 1С высылаем по запросу.

Чем отличаемся

Связать 1С с RabbitMQ можно тремя способами. Два из них работают — но платят за это лишним звеном в схеме или потерей контроля над очередью.

Свой мост на HTTP

Между 1С и брокером ставят сервис-посредник. Его нужно где-то развернуть, обновлять, мониторить и чинить в три часа ночи. Ручное подтверждение, prefetch и повторную доставку придётся написать в нём заново — а заодно решить, что делать, если упал сам мост.

AMQP 1.0 через шину

Платформа умеет AMQP 1.0 и может ходить в RabbitMQ 4.x. Ценой возни с HTTP-заглушкой и без контроля над prefetch, ручным ack/reject и топологией очередей: что даёт механизм — тем и пользуетесь.

Компонента напрямую

1С разговаривает с брокером по AMQP 0.9.1 сама. Подтверждение, темп приёма, обменники и очереди — из встроенного языка, разворачивать рядом нечего, промежуточных звеньев, которые могут упасть, нет.

Отдельный разговор — реализации, которые уже пробовали писать до нас. Вот грабли, на которые там наступают чаще всего, и что сделано здесь.

Как это работает внутри

Компонента — не обёртка над консольной утилитой и не клиент, который просыпается по расписанию. Внутри неё живёт собственное соединение с брокером и отдельный поток, который его обслуживает, пока 1С занята своими делами. 

поток 1С                          фоновый поток компоненты
─────────────────────────────     ────────────────────────────────
BasicPublish(...)   ──задача──►   отправка кадра брокеру
   ждёт ответа                    ожидание данных, процессор свободен
   ◄─── управление вернулось ──   пришло подтверждение — будим вызов

BasicConsume(...)   ──задача──►   подписка на очередь
   ...форма живёт своей жизнью    пришло сообщение
   ОбработкаВнешнегоСобытия ◄──   внешнее событие в 1С
   BasicAck(deliveryTag) ─────►   подтверждение уходит брокеру

Соединение живёт в своём потоке

После Connect поднимается фоновый поток с событийным циклом. Он спит в системном ожидании и просыпается, когда пришли данные, — поэтому простаивающее соединение не стоит вам процессорного времени.

Все вызовы идут через этот поток

Клиентская библиотека AMQP не рассчитана на работу из нескольких потоков сразу. Каждый вызов из 1С ставится в очередь к потоку цикла и выполняется там — иначе отправка кадра и ожидание ответа разъезжаются, и ответ брокера теряется.

Снаружи всё синхронно

Внутри асинхронность, а в коде 1С — обычные вызовы, которые возвращают управление, когда брокер ответил. У каждого ожидания свой срок: не ответил — исключение и текст в GetLastError, а не зависший сеанс.

Ресурсы закрываются по порядку

Сначала AMQP-соединение, потом сокет, потом поток цикла. Порядок задан устройством классов, поэтому он один и тот же при штатном закрытии, при обрыве и при уничтожении объекта в 1С.

Свой транспорт под каждую ОС

На Linux — libevent, на Windows — сокеты POCO с отключённой задержкой Нейгла и отдельным сокетом для пробуждения цикла. Наверх обе платформы отдают одинаковый набор методов.

Компонента не мешает платформе

Рантайм C++ влинкован статически, поэтому в процессе 1С не появляется второй копии библиотек. Имена свойств и методов выделяются через менеджер памяти платформы — так, как того требует Native API.

Как это выглядит в коде

Подключаем макет, отправляем заказ, принимаем ответы. Опрашивать очередь в цикле не нужно — сообщения приходят сами.

ПодключитьВнешнююКомпоненту("ОбщийМакет.BlackRabbitMQ", "BRMQ", ТипВнешнейКомпоненты.Native);
Клиент = Новый("AddIn.BRMQ.BlackRabbitMQ");

Клиент.Connect("rabbit.local", 5672, "user", "pass", "/", 0, Ложь, 30);
Клиент.DeclareQueue("orders", Ложь, Истина, Ложь, Ложь, 0, "");

// Отправка: строка вернёт управление только когда брокер подтвердит приём
Клиент.CorrelationId = "order-1024";
Клиент.BasicPublish("", "orders", ТелоJSON, 0, Истина, "");

// Приём: подписываемся один раз, дальше сообщения приходят сами
Клиент.EnableExternalEvent(Истина);
Клиент.BasicConsume("orders", "", Ложь, Ложь, 50, "");

Процедура ОбработкаВнешнегоСобытия(Источник, Событие, Данные)
    Пакет = ПрочитатьJSON(Данные);       // тело, deliveryTag и свойства сообщения
    ОбработатьЗаказ(Пакет["body"]);
    Клиент.BasicAck(Пакет["deliveryTag"]);   // подтверждаем, когда заказ уже обработан
